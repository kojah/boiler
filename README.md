# Boiler

Boiler generates Go from local `text/template` recipes. A **recipe** supplies
reusable templates and supported field **rules**. A **target** applies a recipe
to a Go struct and chooses a rule for every field. An **output** groups targets
into one generated Go file.

Every field needs an explicit rule, including fields deliberately kept, hidden,
or omitted. Adding a field fails generation until every target handles it.
The compiler owns source inspection, field coverage, configuration validation,
imports, formatting, diagnostics and publication. Recipes own generated behavior.
There is no built-in registry of snapshot, view, traversal or key operations.

## Running

Build the CLI with Go 1.27 or newer:

```sh
go install github.com/kojah/boiler/cmd/boiler@latest
boiler generate --config boiler.yaml
boiler generate --check --config boiler.yaml
boiler check --config boiler.yaml --output internal/output/boiler_views_gen.go
```

For compiler development, `make build` generates the example and builds all
packages. `make generated-check` verifies freshness, `make vet` checks Go code,
and `make test` runs the tests when requested. Consumers can keep a sibling
checkout linked as `tools/boiler -> ../../boiler`, with a separate pinned Go
tool module for clean clones and CI.

Boiler reads Go syntax without loading or type-checking packages, so it runs
before other generators on a cold checkout. The ordinary Go build checks the
output. Generated files carry `// Code generated by boiler; DO NOT EDIT.` and
have no runtime dependency on Boiler. This repository ignores generated Go; consumers can choose to commit it.
Publication refuses to overwrite handwritten files and removes obsolete
`boiler_*_gen.go` files in configured packages when all outputs were compiled.
Compilation renders the entire selected batch before publication starts;
publication replaces individual files atomically, not the whole batch.

## Configuration

The default entry point is `boiler.yaml`. It owns discovery and shared settings:

```yaml
version: 1
sources:
  - boiler/*.boiler
readonly: internal/support/readonly
recipes:
  snapshot: boiler:snapshot
  view: boiler:view
```

Targets live in package-named files, conventionally collected in `boiler/`:

```text
boiler.yaml
boiler/
  value.boiler
  output.boiler
```

For example, `boiler/output.boiler` contains:

```text
package "internal/output" {
    output "boiler_publication_gen.go" {
        snapshot snapshotKind(Kind) receiver(p *publication) {
            // Every Kind field has an explicit rule here.
        }
    }

    output "boiler_views_gen.go" {
        view KindView(Kind) {
            // Every Kind field has an explicit rule here.
        }
    }
}
```

The filenames are a convention, not package resolution: the `package` declaration
determines the destination. Distinct packages with the same name can use descriptive
filenames such as `instance-output.boiler` and `report-output.boiler`.

Source globs use Go `filepath.Glob` syntax (`*`, `?`, character classes); recursive
`**` patterns are rejected. Every pattern must match at least one regular
`.boiler` file. Overlapping matches are deduplicated, then all sources are parsed
in lexical filename order. Within each file, block order is preserved. Shared
aliases are resolved after all sources are read, with no order-dependent overrides.
Duplicate aliases, settings and resolved output paths fail validation.

A target is `RECIPE NAME(TYPE) OPTION(ARGUMENTS)... { FIELD_RULES }`.
Target names are unique per output and type, so a recipe that emits methods can
use one name, such as `Add`, for several receiver types; Go type checking still
rejects two plain functions sharing a name.
A package block supplies the directory once for all its output filenames.
For example, `package "internal/example"` with `output "boiler_graph_gen.go"`
resolves to `internal/example/boiler_graph_gen.go`. `--output PATH` selects that
full manifest-relative path. Top-level outputs also accept a path relative
to the configuration base. Recipe names and option names are extensible: the parser has no built-in snapshot or view keywords.

Field groups are explicit: `ID, Name = keep` means the same as separate rules
for `ID` and `Name`. Generation still follows Go field declaration order.
Duplicate fields, including overlaps between groups, are errors. There are no
wildcards or implicit defaults for fields added to a struct.

A space separates a rule name from its word arguments: `call node` is the
`call` rule with argument `node`. Parentheses compose nested rules:
`each(call node)` and `entries(call ref, keep)`. This rule grammar is separate
from the parenthesized options in a target header.

Options accept written values, quoted strings, and comma-separated arguments:

```text
view NodeView(Node) holder(value) doc("Reads a published node.") {
    ID, Edges = get
    Owner = wrap NodeView
}

key nodeKey(Node) result(NodeKey) params(ownerID OwnerID, typeID TypeID) {
    ID = to id
    Owner = to owner from ownerID
    Dynamic = to dynamic from typeID
    Edges = omit
}
```

The recipe schema interprets these values. `declare(false)` is a boolean;
`doc("false")` is a string. `params(...)` is a list of name/type bindings.
Commas inside strings or nested Go type brackets do not split arguments.
Target headers and nested rules can span lines. Field rules end at a newline,
semicolon or closing brace. `//` and `/* ... */` comments are supported.

Package paths are relative to the manifest, not the source file. Outputs inside a package must be bare
filenames: subdirectories belong in another package block. Package blocks contain
only outputs, cannot be nested, and must contain at least one output. Multiple
blocks for the same package are allowed; duplicate resolved output paths are
errors, including collisions with top-level outputs. Generation retains source
block order.

In project mode, source globs, recipe paths, package paths and output paths are
relative to the YAML manifest directory. Source patterns and output paths must
stay below that directory. Recipe paths may use `..` within the same module.
Boiler finds the module through the nearest parent `go.mod`. It does not fetch
packages or execute plugins.

Standalone `.boiler` files remain supported with `--config FILE.boiler`. They
can declare `recipe` aliases and `readonly` directly and resolve paths from
their own directory. This is useful for self-contained examples. The parser and
syntax are the same in both modes. Shared declarations in project sources are
allowed, but cannot override declarations in the manifest or another source.

[examples/immutable](examples/immutable) demonstrates standalone loading,
snapshots and views, including handwritten identity-preserving hooks.
YAML describes project and recipe configuration; `.boiler` describes targets.

## Frontend architecture

The frontend is a separate standard-library-only package,
[internal/syntax](internal/syntax). `syntax.Parse(filename, source)` is a pure
in-memory operation: it cannot load recipe files, inspect Go packages or emit
code. It scans tokens using `text/scanner`, then produces a position-bearing AST
with recipe declarations, source-ordered package/output blocks, targets, unbound
option arguments, field groups and recursive rule expressions. Comments are whitespace, not retained
trivia. This is a syntax tree, not a formatting-preserving concrete syntax tree.

The stages have explicit boundaries:

Before parsing, `config_files.go` reads the project manifest and expands globs.
It passes each file's text to the pure frontend, combines the positioned trees,
and merges shared settings after lowering. Discovery is not a parser feature.

1. **Scan and parse:** source text to syntax AST; report malformed syntax at its
   filename, line and column. Rule and argument nesting are bounded at 64.
2. **Lower configuration:** `config_lower.go` resolves package-relative output
   paths, expands field groups and checks duplicate recipe, setting, option and
   field bindings. It produces `Config`,
   `Output`, `Target` and `Rule` values with no AST references. `Load` then checks
   output paths and declared recipe aliases.
3. **Resolve and validate:** `Compile` loads recipes and Go declarations, binds
   options according to recipe schemas, and checks field coverage and rule shapes.
4. **Render and publish:** templates produce Go, then formatting and the existing
   output ownership/freshness checks run.

The dependency is one-way: Boiler imports `syntax`; `syntax` imports neither
Boiler nor recipe/Go-inspection machinery. Option schemas and rule semantics
stay in the compiler and recipe layer. Syntax tests can use nonexistent recipe
paths and source types because parsing does not resolve them.

## A recipe directory

```text
recipes/snapshot/
  recipe.yaml
  rules.yaml
  target.go.tmpl
  rules.go.tmpl
```

`recipe.yaml` selects the entry template, template files and separate rule file:

```yaml
version: 1
entry: target
templates: ["*.go.tmpl"]
rules: rules.yaml
options:
  receiver: {kind: receiver}
```

`local: true` restricts the source to a struct in the output package. Otherwise
qualified structs such as `core.MemoryCell` are allowed when their fields are
exported. Field types of a qualified struct are spelled as the output package
writes them: that package's own type names gain the configured qualifier, so
a `*Inner` field of `q.Outer` resolves the `q.Inner` target. Templates and rules paths must stay below the recipe directory.
Template globs are sorted, duplicate filenames are errors, and missing template
values fail rather than silently rendering `<no value>`.

Option declarations support `required: true` and `default: VALUE`. Unknown options
are errors. Supported kinds are:

| Kind | Template value |
| --- | --- |
| `string` | String; omitted defaults to empty |
| `identifier` | Valid nonblank Go identifier |
| `type` | Written Go type expression; its qualifiers are imported |
| `bool` | Boolean; omitted defaults to false |
| `receiver` | `.Name` and `.Type` parsed from `p *publication`; omitted is empty |
| `params` | List of `.Name`/`.Type` pairs; names must be unique |

Bindings reserve `in` and `out`. Recipe templates can impose additional
constraints with `assert`. The compiler validates syntax, not type correctness.

## Field rules

The separate `rules.yaml` for snapshots includes:

```yaml
keep: {}
clone:
  accepts: [slice, map]
call:
  args: [1]
each:
  accepts: [slice, map]
  children: [element]
entries:
  accepts: [map]
  children: [key, element]
```

A rule selects the same-named template unless `template:` overrides it. `args`
lists allowed argument counts (default `[0]`). `accepts` restricts syntactic
shapes to `other`, `pointer`, `slice` or `map`; omission accepts any shape.
`children` declares the number of nested rules and whether each sees the parent
shape's `element` or `key`. Rules are validated recursively before rendering,
including rules whose templates ultimately emit nothing. Nesting is bounded
at 64 levels.

A field selection such as `entries(call ref, keep)` is parsed as an `entries`
rule with two child rules. Arguments are words such as identifiers or qualified
names; they are not arbitrary Go expressions. Templates validate their meaning.

## Template API

An entry template receives:

- `.Name`, `.Type`, `.Recipe`: target name, written source type, recipe alias.
- `.Options`: validated values and defaults from the recipe declaration.
- `.Fields`: source declaration order; each has `.Name`, `.Shape`, `.Rule`.
- `.Readonly`: full import path from the config's optional `readonly` setting.

A shape exposes `.Kind`, `.Written`, `.Element`, `.Key`, and `.Type`.
`.Written` examines source spelling without adding imports. `.Type` renders
that spelling and registers its imports. Elements/keys are absent when they do
not apply; expansion follows named local containers with the same syntax-only
limits as source inspection.

A rule has `.Name`, `.Args`, and `.Children`. `emit FIELD DESTINATION` runs its
selected template with `.Target`, `.Field`, `.Rule`, `.Shape`, `.Dst`, and
`.Depth`. `child CONTEXT INDEX DESTINATION` runs a nested rule with the selected
key/element shape and incremented depth. Destination is an expression supplied
by the recipe, not a compiler-defined write policy.

For example, the clone template is ordinary Go with substitutions:

```gotemplate
{{define "clone"}}
{{if eq .Shape.Kind "slice"}}
{{.Dst}} = {{import "slices"}}.Clone({{.Dst}})
{{else}}
{{.Dst}} = {{import "maps"}}.Clone({{.Dst}})
{{end}}
{{end}}
```

The snapshot recipe starts with `out := in`. Its field rules rewrite those
already-copied values; container templates preserve that convention when
calling child rules. That convention belongs to the recipe, not the compiler.

Additional helpers, alongside standard `text/template` functions:

| Helper | Contract |
| --- | --- |
| `import PATH` | Register import and return a deterministic available qualifier |
| `qualified EXPR` | Resolve existing source qualifiers in a written expression |
| `fresh PREFIX` | Allocate a deterministic identifier, avoiding source names and known imports |
| `ident NAME` | Validate a nonblank Go identifier |
| `assert BOOL MESSAGE` | Fail generation with a contextual error if false |
| `arg RULE INDEX DEFAULT` | Read an optional argument |
| `comment TEXT` | Render text as Go line comments |
| `targetFor RECIPE TYPE` | Resolve one target in the same output, returning name/type/options; missing or ambiguous is an error |
| `structFields TYPE` | Inspect another struct's fields for projection coverage |
| `dict KEY VALUE ...` | Create template-local bindings |
| `put DICT KEY VALUE` | Bind once; duplicate is an error |
| `take DICT KEY` | Consume a binding; absent/already used is an error |
| `empty DICT` | Require all bindings to have been consumed |

Templates are trusted project source. Use ordinary template whitespace trimming
(`{{-` / `-}}`) to control layout. Boiler applies `go/format` to complete files.
Errors identify output, target and (during field expansion) field; template
execution errors include template filename and line. Invalid generated Go is
returned in the error for inspection, without publishing it.

## Supplied recipes

All implementations are readable under [recipes](recipes) and embedded in the
CLI. Select one with `boiler:NAME`, for example `snapshot: boiler:snapshot` in
the project manifest or `recipe snapshot = "boiler:snapshot"` in a standalone
file. Bundled recipes follow the compiler version, so pinned builds are reproducible.
To customize a recipe, copy its directory into your project and point the alias
at that local path instead. Both sources use the same loader and template engine.

The view recipe expects the consumer's `readonly` package to provide `Slice[T]`,
`Map[K,V]`, `Borrow` and `BorrowMap`. The example includes a minimal implementation;
Boiler imposes no runtime dependency on consumers.


| Recipe | Options | Field rules |
| --- | --- | --- |
| `snapshot` | optional `receiver` | `keep`, `zero`, `clone`, `snapshot`, `call NAME`, `func NAME`, `method NAME`, `each(RULE)`, `entries(KEY, VALUE)` |
| `view` | `receiver`, `value`, `holder`, `declare`, `doc` | `hide`, `get [NAME]`, `wrap TYPE [NAME]`, `list TYPE ONE MANY` |
| `visit` | required `child` | `keep`, `apply`, `each` |
| `transform` | required `child` | `keep`, `apply`, `each` |
| `key` | required `result`, optional `params` | `omit`, `to FIELD`, `to FIELD from PARAM` |

Snapshots retain nil containers. `clone` is shallow; `each` and `entries` apply
nested rules to copied contents. `snapshot` resolves another target using the
same recipe alias and struct type, copying pointer values into fresh storage.
`zero` is only valid on top-level fields. Shared/cyclic identity stays in
handwritten hooks selected by `call`. `func` permits qualified function names;
`method` invokes a method on the field value.

Views default to `receiver: v`, `value: value`, `holder: pointer` and
`declare: true`. Pointer views generate `Valid()` and zero-returning getters
for empty views. Value holders omit `Valid()`. `declare: false` attaches methods
to a handwritten type. `get` wraps containers using the configured read-only
package. `list` generates count, indexed access and iteration methods.

Keys may project a qualified struct whose fields are exported into a result
type owned by the output package.

Visits stop when a callback returns false. Transforms rebuild traversed slices
and preserve other fields. Keys require every result field and every parameter
to be consumed exactly once; caller-supplied IDs keep projection pure.

## Limits

Generic structs and packages outside the module are unsupported. Source
inspection does not fully resolve aliases or foreign named containers; use
explicit hook rules there. Go builds remain responsible for type checking and
comparability. A recipe can define its own rules without changing or rebuilding
the compiler. Sophisticated algorithms should remain handwritten hooks rather
than becoming large template programs.
